## 阶段〇：起点与现实的落差

起点是一份现成的搭建文档。核对下来，**7 处假设与实机不符，其中 2 处会直接导致按文档执行失败**：

| 文档假设 | 实机 | 后果 |
|---|---|---|
| 驱动 ≥580 才能用 cu130 | 内核驱动 535.154.05 | 差点放弃 cu130（见坑 1） |
| `git clone github.com/...` | GitHub **完全不通** | **安装步骤全部失效** |
| `download.pytorch.org` 装 torch | HTTP **403** | **装不上 torch** |
| 90 GB 内存 | 78 GB | offload 空间更紧 |
| 独立 `/data` 盘 | 无，`/` 剩 350 GB | 目录规划要改 |
| modelscope CLI 下模型 | 可用但**单线程 0.65 MB/s** | 75 GB 要下 31 小时 |
| ffmpeg 已有 | 未安装 | — |

**教训：拿到任何搭建文档，先花 20 分钟核对硬件和网络，再动手。**
这次的核查花了约 15 分钟，省下的是后面几个小时的返工。

## 坑 1：我把 cu130 判死了，又靠实测救回来

`nvidia-smi` 显示驱动 `535.154.05`，而 CUDA 13 官方要求 ≥580。
我据此判断 **cu130 不可用**，准备退到 cu128 + `fp8_scaled` 模型。

但有个矛盾信号：`nvidia-smi` 头部却写着 `CUDA Version: 13.0`，而且机器上装着 `nvcc 13.0`。
顺着这个矛盾查下去，发现了：

```
/usr/local/cuda-13.0/compat/libcuda.so.580.126.20     ← CUDA 前向兼容层
```

用 ctypes 直接问驱动 API：

```python
ctypes.CDLL("libcuda.so.1").cuDriverGetVersion(...)   # → 13000 = CUDA 13.0
```

**cu130 完全可用。** 内核模块虽是 535，用户态驱动是 580.126.20。

**但有个前置条件**：必须显式设 `LD_LIBRARY_PATH=/usr/local/cuda-13.0/compat`。
不设的话 torch 会解析到 `/usr/lib/x86_64-linux-gnu/libcuda.so.1`（真 535），报：

```
NVIDIA driver on your system is too old (found version 12020)
torch.cuda.is_available() → False
```

**这个判断值多少**：如果当时认了 535 的结论，就会用 `fp8_scaled` 模型。
后来 ComfyUI 日志证实 `int8_convrot` 走**原生 kernel**、`nvfp4` 走**模拟路径**——
选型直接影响画质和速度。

**教训：遇到矛盾信号不要挑一个信，去找能一锤定音的实测。**
`nvidia-smi` 的版本号在容器里可能是宿主机的、可能是兼容层的，
`cuDriverGetVersion()` 才是程序实际会拿到的那个。

## 坑 2：GitHub 不通，整套安装步骤作废

文档里所有 `git clone git@github.com:...` 全部超时。ghproxy、raw.githubusercontent 也不通。

**解法**：`gitcode.com`（CSDN 的 GitHub 镜像）。路径规律是
`gitcode.com/gh_mirrors/<仓库名前几个字母>/<仓库名>`：

| 要的东西 | gitcode 路径 |
|---|---|
| ComfyUI | `gh_mirrors/co/ComfyUI` ✅ 有 v0.28 ~ v0.34 全部 tag |
| ComfyUI-Manager | `gh_mirrors/co/ComfyUI-Manager` ✅ |
| ComfyUI-KJNodes | `gh_mirrors/co/ComfyUI-KJNodes` ✅ |
| SageAttention | `gh_mirrors/sa/SageAttention` ✅ **注意不是 `sag/`** |

`gh_mirrors/sag/SageAttention` 也存在，但那是 **Windows 分支**（tag 全是 `v2.2.0-windows.postN`）。
拿错了会编译失败。

**另一个死胡同**：pypi 上有个叫 `comfyui` 的包，HTTP 200 看着能装——
拉下来一看是 **0.0.1 占位包**，不是本体。别浪费时间。

**教训：镜像站的仓库路径没有统一规律，必须逐个验证 `git ls-remote` 能不能通，
而且要检查 tag 列表确认是不是你要的那个分支。**

## 坑 3：ModelScope 单线程 0.65 MB/s，并发能到 27 MB/s

75 GB 按单线程算要 **31 小时**。这个数字一度让我怀疑整个方案的可行性。

试了并发（`curl -r` 分段），发现：
- 服务端**支持 HTTP 206 Range**
- 6 线程聚合可达 **~27 MB/s**（部分线程命中 CDN 缓存能到 13 MB/s）

改用 `aria2c -x16 -s16` 后，75 GB 实际下了 **约 1 小时**，25 GB 的编码器峰值跑到 23 MB/s。

**第一次并发测试我还测错了**：文件只有 577 MB，我却把字节范围设到 500 MB 以上，
结果 4 个线程里 3 个返回 0 B/s，差点得出"并发无效"的错误结论。重设范围才看到真实情况。

**教训：**
1. **下载慢先测并发，别急着接受单线程的数字。**
2. 自己写的测试也会错。**结果不符合预期时，先怀疑测试本身。**

## 坑 4：pypi 镜像同步进度不一致

volces 镜像快（1.6 MB/s）但**滞后**：`comfyui-workflow-templates` 只到 `0.11.17`，
而 ComfyUI v0.34.2 的 `requirements.txt` 要求 `==0.11.50`。安装直接失败。

查了四个源：

| 源 | 该包最新版 |
|---|---|
| volces | 0.11.17 ❌ |
| 阿里 | 0.11.52 ✅ |
| 清华 | 0.11.52 ✅ |
| pypi.org | 0.1.1（数据异常） |

最终用**阿里源**装成。清华虽然有，但实测只有 236 KB/s，
一次跨清华+阿里的解析卡了 25 分钟没动静，杀掉改用阿里单源后 7 分钟装完。

**教训：镜像不是等价的。快的可能旧，全的可能慢。装不上先换源查版本，别怀疑自己的命令。**

## 坑 5：uv 的跨索引默认行为

```
× No solution found: there is no version of torch==2.9.1+cu130
hint: `torch` was found on volces, but not at the requested version.
```

uv 为防"依赖混淆攻击"，**默认只认第一个包含该包名的索引**。
torch 在 volces 上有（但没有 cu130 变体），uv 就不去交大索引找了。

**解法**：`--index-strategy unsafe-best-match`

**教训：这是安全设计不是 bug。多镜像环境下要显式放开，并且明白放开的是什么。**

## 坑 6：torch 三件套 ABI 不匹配，ComfyUI 启动即崩

我只 pin 了 `torch==2.9.1+cu130`，让解析器自己选 torchvision/torchaudio。
它给了 **torchaudio 2.11.0**。启动报：

```
OSError: /..../torchaudio/lib/_torchaudio.abi3.so: undefined symbol: torch_library_impl
```

torchaudio 2.11 是给更新的 torch 编的，ABI 对不上。

**解法**：三件套一起 pin —— `torch==2.9.1` / `torchvision==0.24.1` / `torchaudio==2.9.1`。

**教训：PyTorch 生态的三件套版本是配套发布的，pin 一个等于没 pin。**

## 坑 7：`pkill -f` 把自己的 SSH 会话杀了（踩了两次）

```bash
ssh host 'pkill -f "ComfyUI/main.py"; ... 后续命令'
```

结果：`Exit code 255`，后续命令全没执行。

**原因**：`pkill -f` 匹配**完整命令行**。而我这条命令的 `bash -c` 命令行里
**字面包含 `ComfyUI/main.py` 这个字符串**，所以 pkill 把自己的父进程也杀了。

第一次踩了没想明白，换了个命令又踩一次，才反应过来。

**解法**：用方括号打断字面匹配：

```bash
pkill -f "ComfyUI/mai[n].py"      # 正则仍匹配目标，但自身命令行不再包含该字面串
```

**连带损失**：被杀的那次会话里有个 `chmod +x`，没执行成，
导致后面 `nohup scripts/fix_torch.sh` 报 `Permission denied`，又浪费一轮。

**教训：**
1. `pkill -f` / `pgrep -f` 在远程一行命令里是危险操作，**永远加方括号**。
2. **命令被意外中断时，要回头确认前面的副作用步骤是否执行成功**，别默认它们成了。

## 坑 8：官方模板用 subgraph 封装，转 API 格式要自己展开

ComfyUI 的 `/prompt` 接口要 **API 格式**（扁平的 `{node_id: {class_type, inputs}}`），
但模板是 **UI 格式**，而且 T2V 模板把 21 个节点封在一个 subgraph 里。

有两条路：
- 在浏览器里加载模板 → Export (API)。可靠但要人工操作，且 driver 就依赖 UI 了。
- 程序化展开。

选了后者：把 subgraph 的 `nodes` / `links` / 输入输出槽映射解出来，
再把 `ComfySwitchNode`（turbo 开关）和 `ComfyMathExpression`（时长→帧数）
**静态解析掉**——turbo 固定走 LoRA 分支，帧数用 Python 算。
21 个节点压成 **16 个**，参数全部可编程控制。

顺带发现模板里的**默认值不能直接用**：`CLIPLoader` 指向 `qwen3vl_32b_minimax_h3_nvfp4_awq`，
而我们按方案下的是 `int8_convrot`，不改就报找不到模型。

**教训：官方模板是给人在 UI 里点的，不是给程序调的。
要做自动化就老实把拓扑解出来，顺便能砍掉一堆 UI 才需要的开关节点。**

## 坑 9：ComfyUI 有结果缓存，把性能测试测成了 15 秒

开启 SageAttention 后跑热启动基准，**15 秒就"完成"了**。
一度以为发现了什么惊人的优化。

**真相**：相同提示词 + 相同种子，ComfyUI 直接返回上次的产物。

**解法**：换 `seed`。给所有脚本加了 `--seed` 参数。

**教训：性能测试出现好得离谱的结果，先怀疑缓存。**
这条同样适用于日常创作——想要新画面必须换种子。

## 坑 10：SageAttention 只能自己编，但比想象中顺利

pypi 上最高只有 **1.0.6**（纯 Triton，`py3-none-any.whl`，无 CUDA kernel）。
带 kernel 的 2.x 只走 GitHub releases 发预编译 wheel——**拿不到**。

只能从源码编。三个关键点：

1. **`TORCH_CUDA_ARCH_LIST=8.9`** —— 只编 Ada。不设会编全架构，时间翻好几倍。
2. **`--no-build-isolation`** —— 必须。否则 pip 在隔离环境里重装一份几 GB 的 torch。
3. **编译期同样要 `LD_LIBRARY_PATH`** 指向兼容层。

原本担心 nvcc 13.0 编 2.2.0（发布早于 CUDA 13）会有兼容问题，**实际没有**。
**2 分 33 秒**编完（12 路并行，CPU 时间 11 分 55 秒）。

收益：算子级 **2.09×**，端到端 **1.99×**（62.85 → 28.90 秒/步）。
代价：INT8 量化注意力有 **3.8% 相对误差**，肉眼看不出退化。

**教训：预编译 wheel 拿不到不等于此路不通。
先看编译前置条件（nvcc、gcc、显卡架构）齐不齐，齐了就编，往往比找镜像快。**

## 坑 11：第一次开 SageAttention，总耗时没变

开启后跑基准：**560.7 秒**，和基线 557 秒几乎一样。差点以为白干了。

**真相**：那轮我重启了 ComfyUI，是**冷启动**。
- 基线（热）：8×62.85 = 503 秒采样 + 54 秒其他 = 557 秒
- Sage（冷）：8×28.90 = 231 秒采样 + **约 330 秒冷加载 46 GB 权重** = 561 秒

省下的 272 秒采样时间，被重新加载权重吃掉了。热启动重测：**280 秒**，1.99× 提速。

**教训：比较性能时冷热状态必须一致。
更稳的做法是比 `秒/步`——它不受模型加载影响。**

## 坑 12：参考图带背景，会把参考场景拖进新镜头

用之前生成的狐狸视频抽帧当参考图，让它出现在"夜晚河边"。
角色保住了，但**开头约 2.5 秒仍停留在参考图的白天秋林场景**，之后才过渡到夜景。

`ref_image_size="max"` 锚定的不只是角色，**是整张图**。

**验证假设**：把角色裁出来贴到灰底上重跑 → 开场立刻是正确的夜景 ✅

**教训：Ref2VA 的参考图必须是干净背景的角色设定图，不能是场景截图。**
这也解释了原文档为什么强调"角色设定图（正侧背、表情）"——但它没说清背景干净是关键原因。

## 坑 13：干净设定图解决了场景污染，却丢了构图

换成灰底设定图后，场景对了，但**狐狸前 4 秒几乎不在画面里**（只有左边缘一点脸），
5 秒后才入镜。模型先把场景搭好，角色再"走进来"。

**原因**：设定图只提供**身份线索**，不提供**空间位置线索**。

**解法**：提示词里显式写构图 ——
`medium shot, the fox is centered in frame from the very first frame`。

**教训：修好一个问题会暴露下一个。
参考图管身份，提示词管构图，两者分工明确，缺一不可。**

## 坑 14：官方的 continuation 模板根本没用 AddGuide

想做镜头衔接，先去看官方 `video_minimax_h3_i2v_continuation.json`——
翻遍 subgraph，**没有 `MiniMaxH3AddGuide` 节点**。它用的是"上镜头尾帧当下镜头首帧"的简单做法。

只能按节点规格自己搭：

```
LoadVideo → GetVideoComponents → GetImageRangeFromBatch(尾部22帧) → MiniMaxH3AddGuide
```

三个接线陷阱：
1. **`AddGuide` 只输出 CONDITIONING**，latent 直通不变 ——
   采样器的 `latent_image` 仍要接 `ReferenceToVideo` 的输出 1。接错就白做了。
2. 接了 `image` 必须给 `vae`；接了 `audio` 必须给 `audio_vae`。
3. `ref_images` 是 AUTOGROW 输入，API 键名是 `ref_images.ref_image_0/1/2...`，
   这个格式只能从模板的 `inputs` 槽名里看出来。

结果很好：接缝在姿势、场景、色调上几乎无跳变，代价是 **+18% 单步开销**。

**教训：官方模板的命名不代表它实现了你以为的功能。
翻不到就去读 `object_info` 的节点规格自己搭——那是唯一权威的接口定义。**

## 坑 15：容器里没有 systemd

计划里写了 systemd 常驻。实际这个容器 **PID 1 是平台的 supervisord**，
而且 `supervisord.conf` 没有 `[include]` 段——想加自己的服务得改平台配置文件，
**有搞挂 sshd / code-server 的风险**（那样就连不上机器了）。

**解法**：`nohup + pidfile` 自己管（`scripts/svc.sh`），
`.service` 文件保留，作为日后迁到真实 VM 的参考。

**教训：容器不是 VM。做常驻服务前先 `ps -p 1` 看 PID 1 是谁。
在别人的进程管理器里插自己的服务，风险要评估清楚——这台机器远程连不上就废了。**

## 坑 16：幂等的价值，用一次崩溃换来的认识

一个 10 秒镜头烧 3.7 分钟 GPU。跑到第 5 个镜头崩了，如果从头来就是 18 分钟白扔。

`pipeline.py` 的做法：**拿到 `prompt_id` 立刻写 manifest**（`os.replace` 原子替换），
然后才开始轮询。重跑时：
- 已完成 → 跳过
- **已提交但没取回 → 只查 `/history` 状态，绝不重复提交**
- 没开始 → 正常跑

实测重跑一个 6 镜头的 job：**0.23 秒，零 GPU 消耗**。

**一个细节**：失败重试时**必须清掉失败的 `prompt_id`**，
否则下次重跑会走进"已提交过"分支，只查状态永远查不到，卡死。

**教训：贵的操作要先记账再执行。
记账要原子（写临时文件再 rename），要在动作之前，不能在之后。**

## 坑 17：累积漂移——识别稳，但构图和色调会漂

连拍 4 镜头后发现：**角色身份完全稳定**（这是最重要的），
但**景别、色温、线条粗细会逐镜头漂移**。

试了"风格前缀自动拼接"（把画风、调色、角色特征固定拼进每条 prompt）：
**部分有效，不是银弹。**

- 色温和画风：**明显改善** ✅
- 景别：**压不住** ❌ —— 衔接镜头的景别由上一镜头结尾的画面决定，文字权重打不过 AddGuide 的图像锚定

**两条实用路线**：
1. 顺着它写——接受上一镜头的景别，据此设计下一镜头的动作
2. 需要强制切景别时，把该镜头设成 `"kind": "r2v"`，放弃无缝衔接换硬切
   （成片里硬切反而像正常剪辑）

有意思的是，最后那条 6 镜头的猫头鹰片子里景别也在变，
但因为**有故事节拍支撑，读起来像刻意的镜头语言而不是失控**。

**教训：技术缺陷在合适的叙事结构下可以不是缺陷。
但你得知道它是缺陷，才能主动利用它。**

## 坑 18：重做一个镜头，必须级联失效下游

`--redo s02` 如果只重做 s02，那 s03/s04 还是**从旧版 s02 用 AddGuide 接出来的**，
拼起来会在 s02→s03 处出现跳变。

所以 `--redo` **默认级联失效下游所有镜头**，`--no-cascade` 才只做单个。

**代价**：重做越靠前的镜头越贵。重做 s02 = 重跑 s02~s06 ≈ 18.5 分钟。

**实践建议**：**先用 5 秒短镜头试提示词，定稿再拉到 10 秒。**

**教训：有依赖链的重算，"只重做一个"通常是错的默认。
把依赖关系编码进工具，比指望使用者每次记得手动处理可靠。**

## 坑 19：商用许可——参考文档说错了，而真正的限制在别处

原参考文档说："本地生成用于商业用途需要 MiniMax 商用许可，Comfy 是唯一官方渠道。"

去把许可原文抓下来读（`../legal/MiniMax-H3-Community-License.txt`，
出处链条见 `../legal/SOURCE.md`），**与原文不符**：

- 第 II 条授予 **royalty-free**（免版税）的使用、复制、分发、改作许可
- 第 VI.4 条："**MiniMax claims no rights over the Outputs you generate.**"
- 第 IV 条只有两条商用要求：年收入 **>2000 万美元**才需单独授权；
  **必须在界面显著标注 "MiniMax H3"**（`shall`，硬性）

而**真正会卡住人的、原文档完全没提的**是**地域**：

## 坑 21：`${var:-默认值}` 不是"var 为空才用默认值"那么简单

收工整理时发现 `svc.sh status` 报「comfyui 已停止」但 API 可达。
两个问题叠在一起：

**问题 A**：进程是手工 `nohup` 起的，没写 pidfile，`svc_pid` 只认 pidfile 所以判定"已停止"。
修法是加进程匹配回落（`pgrep -f` 找到就认领并补写 pidfile）。

**问题 B**（修完 A 才暴露）：PID 显示成 `17433681743368`——同一个 PID 重复两次。

原代码：

```bash
printf "  %-10s %s\n" "$s" "${pid:+运行中 pid=$pid}${pid:-已停止}"
```

意图是"有 pid 就显示运行中，没有就显示已停止"。但：

- `${pid:+A}` → pid 非空时展开成 `A`，空时展开成空 ✓
- `${pid:-B}` → pid 非空时展开成 **`$pid` 本身**，空时才展开成 `B` ✗

所以 pid 非空时两段变成 `运行中 pid=1743368` + `1743368`，拼一起了。
**pid 一直为空的时候这个 bug 完全看不出来**——它只在"修好了另一个 bug"之后才现形。

修法：老老实实写 if/else。

**教训：**
1. `${var:-default}` 是"**取 var，为空则取 default**"，不是"var 为空时才输出"。
   要做条件输出用 `${var:+...}` 或直接 if/else，别把两个混在一起图省事。
2. **一个 bug 可能掩盖另一个。** 修完 A 一定要重新完整验证，
   不能因为"我只改了 A"就假设其余部分照旧正确。
